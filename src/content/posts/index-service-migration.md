## 单机时代的舒适区

索引服务在一台 32 核、128GB 的机器上跑了两年多。2200 万条文件元数据，常驻内存 41GB，查询 P99 稳定在 20ms。舒服到我们几乎忘了它是单点——直到一次硬盘报错，重建索引花了 47 分钟，这 47 分钟里接口全部返回 503。

## 分片和副本，第一个取舍

拆成 16 个 shard，每个 shard 三副本，用一致性哈希加 128 个 vnode 分布。写走 W=2，读走 R=2。

| 配置 | 一致性 | 可用性 | 我们为什么没选它 |
| --- | --- | --- | --- |
| W=3, R=1 | 强 | 任一节点挂掉写入就停 | 重建期间写入全停，不能接受 |
| W=2, R=2 | 可调 | 容忍一个副本挂 | 选了这个 |
| W=1, R=1 | 最终一致 | 最松 | 读到旧数据的概率太高 |

选 W=2/R=2 的意思是：我们接受"可能读到上一秒的数据"，换来单个副本挂掉时读写都不中断。这条线上没人能替我拍板，是我和业务方吵了两次之后定的。

## 全量重建时的资源争抢

重建一开始是串行的，16 个 shard 挨个来，一轮 40 分钟。为了缩短，我改成 8 个并发。结果线上查询 P99 从 20ms 飙到 700ms。

原因不复杂：重建走的是 mmap 顺序扫描 2200 万条记录，page cache 被这批冷数据整体挤出去，线上热查询开始频繁缺页、走磁盘。`iostat` 上 `%util` 顶到 100%，`r/s` 从 200 涨到 6000。后来给重建加了 200MB/s 的限速，P99 回到 60ms 左右。比不动的时候还是差 3 倍，我到现在也说不清这个数是"够用"还是"忍了"。

## 向量时钟写错的那一次

副本之间用向量时钟判断版本新旧。正确的偏序关系是：a 的任何一个分量都不大于 b，且至少有一个分量严格小于 b，才能说 a 先于 b。

```rust
fn happens_before(a: &[u64], b: &[u64]) -> bool {
    a.iter().zip(b).all(|(x, y)| x <= y) && a.iter().zip(b).any(|(x, y)| x < y)
}
```

我当时的实现只留了后半句：

```rust
// 少了 all 那一半
fn happens_before_wrong(a: &[u64], b: &[u64]) -> bool {
    a.iter().zip(b).any(|(x, y)| x < y)
}
```

后果是任意两个不可比的版本都能被判出先后——`[2,1,1]` 和 `[1,1,2]` 之间来回跳，读路径就永远选错那个。故障表现不是报错，而是静默读旧：某个副本返回了 40 分钟前的索引快照，客户端拿到 1.2 万个已经被删除的文件，用户点进去全是 404。这个 bug 藏了两个月，因为平时三副本的时钟几乎总是相同的，只有重建或者宕机修复之后才会分叉。

> 同事 review 时的原话：你这函数对任意两个不同的向量都能返回 true，那它判的不是先后，是"不相等"。

## 现在

改了向量时钟的比较，给重建限了速，加了三副本时钟分叉的监控。迁移真正换来的不是性能——单机的延迟其实更低——而是不用再经历那 47 分钟里所有人干等的日子。分布式给的可用性，代价是每次读都要多问一句：这条数据是哪个版本。
