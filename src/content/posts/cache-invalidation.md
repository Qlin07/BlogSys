## 失效这件事我能想到的四种做法

| 做法 | 一致性窗口 | 实现成本 | 结论 |
| --- | --- | --- | --- |
| 失效广播（pub/sub） | 毫秒级，但会丢消息 | 高：要处理重连、乱序、重复 | 没选 |
| 版本号 + 读时校验 | 无 | 高：每次读多一次版本查询 | 没选 |
| 写时双删 | 秒级 | 中：要处理删除失败与重试 | 部分用 |
| 短 TTL + 主动删除 | 不超过 TTL | 低 | 选了这个 |

这张表是我在一次架构评审前二十分钟画的，画完自己也有点不甘心：三行里有两行的结论是"没选"，理由却只是"成本高"。

## 为什么最后选了最笨的

核心是复杂度预算。广播方案真正难的不是把消息发出去，是"消息丢了怎么办"——订阅端断线重连那段时间的失效请求得存、得重放、还得去重，一套做下来是另一个需要自己维护的小分布式系统。那段时间我们组只有两个人，还要同时维护索引和迁移。

短 TTL 加主动删除的行为可预测得多：写入成功就删 key，删失败就等 TTL 兜底。最坏情况是读到一份不超过 TTL 的旧数据，而不是永久不一致。

TTL 不是随手拍的，我按数据类型分了几档：

| 数据类型 | TTL | 依据 |
| --- | --- | --- |
| 列表页 | 30s | 用户对列表新鲜度的容忍度最高 |
| 详情页 | 5min | 改了要能较快看到，但不要求实时 |
| 用户配置 | 15min | 改得少，但有主动删除兜着 |
| 标签 / 分类 | 1h | 基本不变，只是防缓存永不失效 |

## 主动删除怎么写

```rust
async fn update_profile(&self, id: u64, patch: ProfilePatch) -> Result<()> {
    self.db.update_profile(id, patch).await?;               // 先落库
    if let Err(e) = self.cache.del(&format!("profile:{id}")).await {
        // 删失败不阻断写，交给 TTL 兜底，但要打点
        metrics::counter!("cache.del.failed").increment(1);
        tracing::warn!(user = id, error = %e, "cache delete failed");
    }
    Ok(())
}
```

顺序是先落库再删缓存。反过来（先删缓存、再落库）在并发下会出现一个窗口：读请求把旧值读回来，写回缓存，正好盖住刚写进去的新值。

## 代价和它的边界

明确接受的代价是最长 30s 到 15min 的旧数据窗口。上线前按这个数跟产品对过一遍：列表页 30s 没问题；用户改了昵称，15 分钟内有少数人看到旧的，产品说能接受。如果不接受，那就该换版本号方案，而不是把广播硬塞进来假装它更好。

还有一条必须写清楚：主动删除是 best-effort，不是保证。删除请求超时、网络抖动、或者进程在落库和删除之间被 kill，一致性就完全交给 TTL 兜住。这个"漏了也不会出事"的性质，正是我选它的主要原因——它的失败是有界的。

## 复杂度花去了哪里

省下来的这部分复杂度，我花在了重建索引的限速和消息处理的幂等上。把预算投到那里，比投到一个自己实现的失效广播上更值得——至少那两处出问题时会报错，而失效广播出问题时只会静默地不生效。
