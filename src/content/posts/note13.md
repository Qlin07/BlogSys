# 池化(Pooling)

## 一、池化的动机

为什么池化能优化GC？池化优化了什么？
要解答以上两个问题，要先搞清楚一次普通的分配，到底“贵”在哪里

在.NET中，在托管堆上分配一个小对象，本质上只是移动一个指针。由于Gen0是一片连续内存，分配就是“指针往前挪一格”，所以分配动作几乎就是零成本。真正的成本并不是分配本身，而是分配引发的后续。

### 代价一：分配速率越高，GC越频繁

GC的触发条件之一是"Gen0预算被填满"。分配的越快，GC就被触发得越频繁——GC的代价可不低。

### 代价二：存活对象带来的晋升开销 

在每轮GC结束后，Gen0、Gen1中存活的对象都会往上晋升一级，晋升的过程包括：

- 将对象复制到更老的一代
- 更新引用、修正指针

如果一个对象被反复创建又短暂存活，它可能被复制多次，纯属浪费。

### 代价三：大对象堆的额外压力

LOH只在Gen2回收时处理，回收后默认不压缩，更容易触发碎片化问题

举一个直观的例子：

```C#
// 每个请求都 new 一个 100KB 的 byte[]
void HandleRequest()
{
    byte[] buffer = new byte[100_000];  // 落到 LOH
    // ... 用完就丢
}
```

在计算机高速运行下，每秒都会产生上千个LOH对象，快速堆高Gen2的回收频率。问题在于：这些对象用一次就扔，但我们却承担了分配、回收、晋升、碎片化的全套代价

池化要解决的就是这个问题：既然对象的内容可以重用，那对象本身也应该可以重用。

## 二、池化的核心思路——复用

复用的思路非常简单，符合人的第一直觉：能反复用的东西没必要用完一次就扔，而是放回原处，等待下一次取用。

这就是池化。关键动作有两个：归还和再取。下面通过代码来对比

```C#
byte[] buffer = new byte[100000]; //用时创建，用完就扔
```

```C#
byte[] buffer = ArrayPool<byte>.Shared.Rent(100000); //从池中借取
try{
    //在这里使用buffer
}
finally{
    ArrayPool<byte>.Shared.Return(buffer); //用完后归还，同时清空，防止下一个借用的对象拿到脏数据
}
```

从GC角度看，还有一个更深的区别：被池持有（池通常是静态引用，属于GC Roots）的复用式对象，很快就能从Gen0晋升到Gen2并长期停留，几乎不再参与后续的GC的搬运动作。

所以池化后，系统里幸存的对象总数可能变多了，但是GC变得轻松了。

## 三、池的工作机制原理

### 池到底是什么

池是一种对象，里面存的是引用，不存数据。	

### 在一次 借出-归还 行为中的引用变化

在.NET中，引用型变量在栈上或者对象内部只占一个指针大小的空间。这个指针指向的就是数组对象在堆上的地址。
所以引用变化本质上是指针在各个位置之间是如何被复制和清空的。

#### 借出

假设池的某个规格桶内部就是一段数组式的空闲栈，并用一个`count`标记栈顶。

借用前：

```text
      桶内部 (池对象字段)             堆
1               stack[0]       ─────▶    Array_A (0xAA00)
2    count ->   stack[1]       ─────▶    Array_B (0xBB00)
3               stack[2]       ─────▶    null
          
     count = 2                  局部变量：buffer = null（还没有引用）
```

借用时：

```C#
// 概念上的实现，非真实源码
int idx = --count;          // 栈顶从 2 降到 1
byte[] result = stack[idx]; // 把 stack[1] 的引用“复制”到 result
stack[idx] = null;          // 把 stack[1] 这个槽清空，不再持引用
return result;              // 把引用交给局部变量
```

借用后：

```text
      桶内部 (池对象字段)             堆
1    count ->   stack[0]       ─────▶    Array_A (0xAA00)
2               stack[1]       ─────▶    null
3               stack[2]       ─────▶    null
          
     count = 1          局部变量：buffer ─────▶ Array_B (0xBB00)
```

从指针的变化可以看到，Array_B 这个对象一步都没动，它一直在堆上的 0xBB00。变的只是"谁指着它"。借用前，是桶的槽指着它；借用后，变成你的局部变量指着它。引用被复制出去了，桶放弃了这根线。这就是"取对象"的真相： 不是把对象从池里搬出来，而是把一根指向它的引用复制给你，池自己松手。

#### 归还

触发归还

```C#
ArrayPool<byte>.Shared.Return(buffer); //这行代码触发归还行为
```

归还时

```C#
// 概念上的实现
stack[count++] = buffer;   // 把引用复制进桶的空槽
```

归还后

```text
      桶内部 (池对象字段)             堆
1               stack[0]       ─────▶    Array_A (0xAA00)
2    count ->   stack[1]       ─────▶    Array_B (0xBB00)
3               stack[2]       ─────▶    null
          
     count = 2                  局部变量：buffer ─────▶ Array_B (0xBB00)
                                                           ↑ 仍然在引用
```

注意这里容易被忽略的细节 ：归还后，局部变量`buffer` 依然指向 Array_B ，池的桶也指向它。同一时刻， 有两根引用指着同一个对象 。

所以规范用法里，归还后应该把这个局部引用也清掉（置 null 或让它离开作用域），否则那根引用会额外拖住这个对象，甚至造成"以为还了其实还握着"的误用。

#### 可不可以不还给池，等引用结束直接GC？

理论上可以，因为池不追踪已借出的对象，但是不建议这样做。这种行为非常容易出错：如果引用没有及时断开，可能GC都不会发生，导致无用对象长期占据内存空间，甚至内存泄露，是危险行为，应避免。

### 池实现层面的对比

池在设计上有三个正交的维度，分别是：

- 分档：按容量把空间划分，每档就是一个桶，可以有多档（按2的幂分），也可以单档。
- 容器：每个桶内部，空闲对象按什么顺序取还，一般有栈、队列和单槽。
- 并发分层：多线程无锁访问，分为线程本地栈 / 每核加锁栈 / 全局

本节只讨论前两个，第三个涉及到操作系统的相关内容。

一个具体的池，是三个维度相乘的组合，比如：

- `ArrayPool<byte>.Shared`的桶是按2的幂分的，而其中的每个对象都通过栈管理。
- `DefaultObjectPool<T>` 则是单桶结构，每个桶都是单槽，配合数组控制对象。

下面详细讲桶的存储结构的不同带来的差异


#### 桶的存储结构

桶本身通常通过是由一个按尺寸索引的数组存的（`_buckets[i]`），所以桶的数据结构决定了对象怎么取还，以及性能和行为

##### 方案一：栈

使用栈作为数据结构的例子就是`ArrayPool`

`ArrayPool<T>`的每个桶，本质是一个栈

- 取的时候从栈顶pop一个
- 还的时候压到栈顶


好处是缓存局部性好。刚归还的对象它的内存很可能还在CPU的L1和L2缓存里，马上复用命中率最高。而代价则是少数对象会被反复使用，其余对象闲置。

##### 方案二：队列

如果池管理的资源会随时间失效（比如一条实时网络连接，空闲太久会被服务器关闭）这是就应该使用队列作为数据结构，让每个对象都被定期使用一次，刷新存活时间。
这种管理网络连接的池中存的都是可以随时通讯的建立好空闲连接，当有进程需要通信时就把这个连接给它，等用完了在还。这里管理的**对象是有效连接**，对应的两个状态应该是空闲和忙碌，而不是连接本身的有效和无效

##### 方案三：单槽热路径

.NET 的`DefaultObjectPool<T>` 用了一个 混合结构 ,很能说明"存储结构是可以为性能定制的":

- 它有一个 单独的字段`_firstItem` 存放一个对象,作为"极速通道";
- 其余对象放在一个`ConcurrentQueue<T>` 里。
  借的时候:

- 先用一次 无锁的原子交换 去抠`_firstItem` ;
- 抠到了就直接返回—— 连队列都不用碰 ;
- 只有`_firstItem` 为空时,才去访问队列。
  还的时候同理:先尝试塞回`_firstItem` ,塞不进才入队。

为什么要这么设计?因为很多池在 大多数时刻只有一两个对象 在用。如果每次取还都要走队列(哪怕队列是并发的),也是不必要的开销。用一个字段兜住"只有一个对象"的常见情况,就省掉了队列操作。

这个例子揭示了一条通用规律:池的存储结构,往往是"针对自己的典型使用模式"裁剪出来的,而不是照搬某个教科书数据结构。

### 池的工作原理

使用`ArrayPool<byte>.Shared` 走一遍完整流程，来看池的内部行为：

```C#
byte[] buffer = ArrayPool<byte>.Shared.Rent(100000);
```

这个 Rent 内部大致做了这几件事：

1. 算尺寸 ：你请求 100000 字节，池不按精确值存储，而是向上取整到某个 规格档（bucket） 。

2. 找桶 ：在池里找 ≥100000 的那个最小规格档。

3. 取对象 ：
   - 该桶里有空闲对象 → 弹出一个返回给你；
   - 该桶为空 → 帮你 new 一个符合该规格的。

4. 归还 ：

   ```C#
   ArrayPool<byte>.Shared.Return(buffer);
   ```

   把buffer放回它原本所属规格档的桶里。

可以简单理解为以下流程：

- 调用方对池说“我要一个能装这么多字节的对象”；池把尺寸**向上对齐**到某个规格档 。
- 池检查该规格的桶里有没有空闲对象：有就直接给；没有就新建一个完整对象给调用方（这个过程就是普通分配,池不当"内存中间商"）。
- 调用方用完后把整个对象还回来，由池决定收不收。
- 池**按上限**决定：没到上限就收下囤着；到上限了就丢弃（让对象成为垃圾、交给 GC）。
- 回收的对象不保证清零
- 下次有人来借同规格的对象，池若桶里有现成的，直接复用，跳过新建。


以上过程包含了三个关键机制

#### 关键机制一：按"规格档"分桶，而不是逐个尺寸

这是 ArrayPool 最核心的设计。它不可能为每一个可能的字节数都准备一个桶（那会有无数个桶），所以它 把尺寸	离散化成若干个档位 ，通常是按 2 的幂次分组：

```text
bucket[0] → 尺寸 16
bucket[1] → 尺寸 32
bucket[2] → 尺寸 64
bucket[3] → 尺寸 128
...
```

这带来一个极其重要的后果 ：`Rent(n)`返回的数组，长度通常 ≥ n，而不是恰好等于n。

```C#
byte[] buffer = ArrayPool<byte>.Shared.Rent(100000);
// buffer.Length 很可能是 131072（2^17），而不是 100000
```

使用时必须假设拿到的数组可能比你请求的大 ，使用时应以"我实际需要多少"为准，而不是以`buffer.Length` 为准：

```C#
// 只处理真正写入/需要的部分
Process(buffer, 0, actualLength); //抽象的处理函数，从0到实际长度处理buffer
// 不能以为它就是 100000，或者把多余部分也当成有效数据
```

#### 关键机制二：线程安全通过"分层"实现
池会被多个线程同时 Rent/Return，而 锁是昂贵的 。所以成熟的池实现通常采用 分层策略 ：

- 每个线程一份本地空闲栈 ：线程从自己的本地栈取还， 完全无锁 ，这是最常见、最快的路径。
- 全局兜底池 ：当本地栈空了（要 new）或满了（要丢弃），才去访问共享的全局池，此时才需要同步。
  这样就做到了： 常态操作无锁，只在扩容/收缩这种边缘情况才付出同步成本 。

#### 关键机制三：容量上限与"丢弃"策略

池不会无限增长——否则它自己就变成了内存泄漏。所以：

- 每个桶有上限（比如某个最大值）。
- 当 Return 时如果桶已满 → 这个对象被直接丢弃，不放进池，让 GC 回收。
  这个设计保证了池的最大内存占用是有界的，不会因为偶发的流量尖峰就永久占住内存。

#### 关键机制四：不保证清零

前面提到过，这里再明确一下`ArrayPool.Rent` 的语义边界 ：

它不保证 数组内容是零，可能残留上一次使用者的数据。
这既是它的性能优势（省去了清零的内存写入），也是它的风险点（可能读到脏数据）。如果安全性有要求，你必须自己清零：

```C#
//归还时清零
ArrayPool<byte>.Shared.Return(buffer, clearArray: true); 
//先用Array.Clear()清零，后面在归还
Array.Clear(buffer, 0 , buffer.Length); 
ArrayPool<byte>.Shared.Return(buffer); 
```

## 四、池化的代价与权衡

### 代价一：你接管了对象的生命周期管理

重建式写法里，对象的生死由 GC 和引用的作用域自动决定——几乎不用操心。而池化之后， 归还的责任落到了程序员身上。

这带来两个具体问题：

- 忘记归还 ：对象没回到池里 → 池的复用率下降，逐渐退化成"每次都 new"，池化白做。
- 重复归还 ：同一个对象还两次 → 会导致 同一个数组被两个使用者同时拿到 ，产生数据互相踩踏的严重 Bug。这类问题极难排查，因为它不报错，只是数据偶发错乱。
  所以池化代码 必须 严格遵循`try/finally` 或`using` 模式。这增加了代码的复杂度和出错面。

非常像C++的double free对吧，这就是手动管理对象天然面对的问题。

所以池化代码**必须**严格遵循`try/finally` 或`using` 模式。

### 代价二：对象长期存活，反而可能加重内存

池持有的对象是 GC Roots 可达的，会长期驻留在 Gen2。这意味着一件事：只要池还持有它，GC就永远回收不了它。

考虑一个极端场景：你有个池，某次流量尖峰下池膨胀到缓存了 1000 个 1MB 的大数组。尖峰过去后，如果池的收缩策略不激进，这 1GB 内存可能就这么被池长期占住 。

所以池的容量上限设置非常关键——池是可控的内存占用，不是"越多越好" 。设得太大，就变成了变相的、不受GC管理的内存池。

### 代价三：不保证清零带来的安全与正确性风险

`ArrayPool.Rent` 返回的数组内容可能是脏的，这引发两类风险：

- 安全风险：残留数据可能包含密码、Token、用户隐私。如果是网络缓冲区这类会跨用户复用的对象，泄漏风险很高。
- 正确性风险：如果你的逻辑假设"数组初始为 0"，就会产生难查的 Bug。

应对方式是归还时清零（`Return(buffer, clearArray: true)` ）或用前手动`Array.Clear`——但这又把清零的内存写入成本加回来了，部分抵消了池化的收益。

### 代价四：长度不确定，语义变复杂

这是最核心的判断。池化有收益的前提是： **对象的创建/回收成本显著高于池化本身的维护成本** 。

- 分配频率高、对象大、创建成本高的对象适合池化
- 对象小、创建廉价、生命周期差异大、无法可靠归还的对象不适合池化

### 小心过度优化

如下代码

```C#
// 只为了循环里少 new 一个小对象，就把整个方法池化改造
for (int i = 0; i < 1000000; i++)
{
    var sb = StringBuilderPool.Rent();  // 池化一个廉价的小对象
    // 一些操作...
    StringBuilderPool.Return(sb);
}
```

如果`StringBuilder` 本身很小、循环里也没别的分配压力，这么做可能 比直接 new 更慢 ，还引入了 Bug 风险。这就是"为了池化而池化"的过度优化。

## 五、标准使用方法（.NET中的池化设施）

.NET 里已经内置了几套成熟的池化设施，绝大多数场景不需要自己手写池，直接用这些即可。

### 设施一：`ArrayPool<T>`

用于复用数组，是 GC 优化中最常用的池。

```C#
// 方式一：使用共享池（推荐，进程内全局共享，通常最优）
byte[] buffer = ArrayPool<byte>.Shared.Rent();
try
{
    // 用 buffer，注意 buffer.Length 可能大于申请量
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);  // 必须归还，必要时清零
}
```

```C#
// 方式二：创建私有池（当你需要独立于全局池的容量/隔离时）
var pool = ArrayPool<byte>.Create(
    maxArrayLength: 1024 * 1024,   // 超过此长度的数组不被池缓存
    maxArraysPerBucket: 50);       // 每个规格档最多缓存多少个
```

关于`Create` 的两个参数，含义：

- `maxArrayLength` ：池只缓存不超过这个长度的数组；请求超过它的数组，池会给你分配但归还时不缓存（直接丢弃）。
- `maxArraysPerBucket` ：每个规格档的容量上限，控制池的最大内存占用。

### 设施二：`MemoryPool<T> / RecyclableMemoryStream<T>`

`ArrayPool<T>` 处理的是"一整块连续数组"。但有些场景需要的是可增长的内存块，比如：

- 不知道最终数据有多大，需要边写边扩容
- 需要以`Stream` 的形式读写

这时数组池就不够用了，因为数组 一旦借出长度就固定 ，无法原地增长。对应设施是：

```C#
// MemoryPool<T> 抽象，配合 IMemoryOwner<T> 使用
using IMemoryOwner<byte> owner = MemoryPool<byte>.Shared.Rent(100_000);
Memory<byte> memory = owner.Memory;
// 用 memory，作用域结束自动归还
```

它和`ArrayPool` 的关键差异是：`ArrayPool` 借出的是`byte[]` ，需要你手动`finally` 归还；`MemoryPool` 借出的是`IMemoryOwner<T>` ，实现了`IDisposable` ，可以用`using` 自动归还，降低了忘记归还的风险。

对于"需要`Stream` 且会增长的场景"，生态中常用的方案是`RecyclableMemoryStream` ，它用一个池来提供可复用的`MemoryStream` ，避免大缓冲反复分配。

### 设施三：`ObjectPool<T>`

前面几种都是针对"内存块"的。而`ObjectPool<T>` 是一个通用的对象池，用于复用任意类型的对象，适合创建成本高的对象（如数据库连接、复杂配置对象、需要初始化的重型对象）。

它位于`Microsoft.Extensions.ObjectPool` 包中。核心用法：

```C#
// 1. 定义策略：如何创建、如何归还
public class MyPolicy : PooledObjectPolicy<MyResource>
{
    public override MyResource Create() => new MyResource();       // 池空时怎么造
    public override bool Return(MyResource obj)
    {
        obj.Reset();          // 归还前重置状态
        return true;          // true=放回池；false=丢弃
    }
}
// 2. 创建池
var provider = new DefaultObjectPoolProvider();
var pool = provider.Create(new MyPolicy());
//以上准备工作结束

// 使用
var obj = pool.Get();       // 借
try
{
    // 用 obj
}
finally
{
    pool.Return(obj);       // 还
}
```

注意`Return` 返回`bool` 这个设计：它让你决定这个对象是否值得放回池。返回`false` 就等于丢弃——这正好对应"池容量有界、必要时丢弃"的机制。

### 设施四：ThreadPool 与连接池（广义的池）

池化的思想不限于内存对象，还有两个更宏观的内置池：

- ThreadPool（线程池） ：复用线程，避免频繁创建/销毁线程的系统开销（线程是操作系统资源，创建成本远高于对象）。
- 连接池（如 ADO.NET / HttpClient） ：复用数据库连接/HTTP 连接，避免反复建立 TCP 连接、握手、认证。

它们和对象池在思想上完全一致： 把昂贵的资源建好后留住复用 。区别在于它们管理的是操作系统级资源，付出的代价更高，因此收益也更大、更必须。
