# 垃圾回收

## 分代回收

### 一、基础思想——弱代假说

最简单粗暴的GC思路是：**每次回收都扫描整个堆**。这样能保证正确，但是有一个显而易见的问题：**每次都要遍历所有对象**，效率非常低下。

C# 程序所依赖的垃圾回收，由 .NET 运行时提供，而 .NET 采用的优化策略就是**分代回收(Generational GC)**。这是一个“偷懒”但又聪明的策略，支持它的两个**经验规律**就是**弱代假说**：

1. 大多数对象刚创建不久就会变成垃圾
2. 存活越久的对象，继续存活的概率越大

既然如此，那么就可以把堆分类为“新对象区”和“旧对象区”：

- 频繁回收“新对象区”：这里可能会有更多垃圾，一次扫描就能回收大多数垃圾
- 较少回收“旧对象区”：这里大多是活对象，回收收益低。

### 二、三代结构与晋升机制 

#### 1.三代结构

.NET 的**小对象堆**在逻辑上划分为三代，从新到旧分别是：

- Gen0：新分配的小对象先进入这里，回收频率最高
- Gen1：短期对象与长期对象的缓冲区，回收频率中等
- Gen2：长期对象，回收频率最低

在内存上，Gen0与Gen1都保存在同一个内存段里，这个段叫作**“临时段”**，Gen2位于独立的段中。

> 大对象堆中的对象在逻辑上被当作gen2，相关知识点后续展开

#### 2.晋升机制

**晋升**指对象如何从Gen0到Gen1再到Gen2，核心规则是：

- 在一次GC中留存下来的对象，会被晋升到下一代。
- 对象到达Gen2后不再晋升。

需要注意的是，所谓的回收第N代，不是只回收第N代，而是**连同它所有更年轻的对象一起回收**

- Gen0回收：只回收Gen0。留存对象晋升一级
- Gen1回收：回收Gen1和Gen0。留存对象晋升一级
- Gen2回收（也称作**完整回收/Full GC**）：回收Gen0/1/2。Gen2留存对象无法继续晋升，其余留存对象晋升一级

#### 3.触发回收的预算（budget）

每一代都有一个预算（budget），即该代允许占用的内存额度。当在Gen0上的新分配量超过Gen0预算时，就触发一次Gen0回收。各代预算是由GC动态调整的：如果某代的存活率很高（说明里面活对象多），GC会倾向于调大它的预算，减少回收频率。

> 具体预算数值随.NET版本、系统位数（32/64位）、GC模式而不同，有时会动态调整预算。

### 三、GC Roots(根)

#### 1.什么是根

根是**GC 进行可达性分析时的起始引用 。**

GC判断对象的死活不是依据引用计数，而是**可达性**

- 从所有根出发，沿着引用关系一路遍历，能走到的对象=存活，不能走到=垃圾
- 根 自身被视为无条件存活，并且是活对象链的起点。

#### 2. `.NET`中的根包括哪些

- 静态字段
- 线程栈上的局部变量和方法参数
- CPU寄存器
- GC句柄
- 终结队列（等待终结器执行的对象）

### 四、跨代引用与解决方法

#### 1.跨代引用

假设堆里由两个对象：

- 对象A在Gen2，它有一个字段`A.C`引用着C;
- 对象C在Gen0，除了被A引用外没有任何根或者其他对象引用C。

现在触发一次Gen0回收，那么问题来了：

- GC从根出发，找不到任何指向C的路径（能指向C的路径是root→...→A→C，但是A在gen2，根不会寻路到A）
- GC误判C是垃圾，回收C——可C还被A引用着。

这就是**跨代引用问题**，

#### 2.解决思路：记忆集（Remenbered Set）

把**老代指向年轻代的引用单独记录**下来，这个记录集合就是记忆集。在GC时，除了扫描根+年轻代，再额外扫描记忆集就能避免误删。

#### 3.维护记忆集——写屏障（Write Barrier）

现在问题变成：什么时候往记忆集里面写？那就是**当程序执行“把引用写入对象字段”这个操作时**。

.NET的做法是：在编译“引用类型字段赋值”这条语句时，**在赋值处插入一小段辅助代码**，这段代码就是“写屏障”。

- 在引用写入时，判断这次写入是否落在一个“较老的代”的对象上；
- 如果是，就把该对象所在的卡片标记为脏（见下一节）

#### 4.卡片表（Card Table）

如果记忆集精确记录每一个老代对象，空间开销会很大。所以.NET（以及JVM）采用一种**粗粒度**的实现：**卡片表**

具体结构是：

- 把堆内存按固定大小切块，每块称为一张卡片。.NET中卡片大小是256字节
- 另外维护一张位图数组，这就是卡片表，每张卡片对应一个字节/位；
- 某张卡片内只要存在一条老代的引用，就在卡片表上把这张卡片标记为脏（dirty）。

所以卡片表是记忆集有取舍的近似实现：精确不到对象，而是256字节的内存块。这样就能降低标记一次脏位的成本，代价是回收时会多扫描一些脏卡片上没有跨代引用的对象。

#### 5.回收时如何使用卡片表

回收年轻代时，GC的扫描范围变成：根+年轻代+卡片表中“脏卡片”覆盖的内存区域。GC把这些区域当作额外的根来扫描，从而把`A.ref → C`这条边纳入可达性分析。

扫描完成后，卡片表会被清零（复位），等待下一轮写入再次标记。

#### 6.代价

写屏障开销：每一次引用字段赋值，都要多执行一小段代码（判断与可能会写卡片表）。

卡片表内存：选哟额外一块位图内存；

精度损失：卡片是粗颗粒度的，回收时可能扫到一些没有跨代引用的对象的内存，属于“宁可扫错，不可放过”。

尽管如此，比起整个扫描整个gen2，这个代价还是可以接受的。这正是分代回收成立的前提。

## GC触发时机与完整流程

### 一、GC什么时候触发

主要有三类触发条件（前两类是正常自动触发，第三类一般不推荐）

#### 1.分配预算超限

这是最常见的情况。每一代都有一个预算，当新分配导致某一代超预算时，就会触发回收。

- 触发点通常是Gen0预算被耗尽，然后触发一次Gen0回收；

- 如果Gen0回收后释放的内存依然不够继续分配，就升级回收gen1，还不够就gen2。

  > 这里的不够分配是指代内预算的不够分配，如果Gen2回收后仍不够，GC会依次尝试
  >
  > 1. 扩展堆：申请新的段。GC向OS申请新的内存段。
  > 2. 深度回收：如果拿不到新段、或者需要腾空间，GC会采取更激进的手段，例如
  >    - 触发一次压缩式完整GC
  >    - 对LOH启用压缩，减少大对象堆碎片
  > 3. 还是拿不到内存空间：报错`OutOfMemoryException`。一般有以下原因
  >    - 物理内存 / 提交限制被占满
  >    - 进程地址空间耗尽（多见于32位系统）
  >    - 配置了硬上限：.NET Core可用`GCHeapHardLimit`指定堆的最大值，超过就OOM。

#### 2.系统物理内存不足

操作系统或者宿主（host）发出内存不足通知时，GC会被触发，这时会更倾向完整回收（Full GC）

#### 3.显式调用`GC.Collect()`主动请求回收。

官方文档明确说明：**绝大多数情况下不应该手动调用**，它主要用于测试或特殊场景。

> 补充说明：在.NET 8中，GC触发的内部原因被细分为18种，但归纳总结就是以上三类。

### 二、一次完整的回收流程

一次回收总共被划分为三个阶段：标记、重定位、压缩。完整流程如下：

- 触发：满足触发条件时，GC启动
- 挂起应用线程（STW）：暂停所有应用线程。这一步是为了让GC拿到一个引用关系不会变化的稳定状态。
- 标记：从根出发，遍历整个对象图，把所有可达对象标记存活。
- 计划：GC决定如何整理堆：计算存活对象的新位置、决定这次是压缩还是清扫。同时生成“对象从旧地址到新地址”的映射。
- 重定向：根据第四步的映射，更新所有指向被移动对象的引用（包括根里的引用和堆内对象之间的引用），让它们指向新地址。
- 压缩或清扫（Compact / Sweep)：
  - 压缩：把存活对象移动到一起，消除已清除对象留下的零散内存空间。这是SOH的默认行为。
  - 清扫：不移动对象，只把已清除对象留下的空间串成“空闲列表”供后续分配。当压缩代价不划算时采用；LOH默认不压缩。
- 恢复应用线程：应用线程继续运行，此时堆已整理完毕。

## 并发标记

在回收流程中的标记阶段，传统上是Stop-The-World(STW)式的，对Gen2这种大的、活对象多的场景，标记可能耗时几十几百毫秒，造成卡顿。并发标记就是为了解决这个问题。

### 一、基本思路

并发标记的基本思路是：让GC的标记线程和应用线程同时运行，把一次长暂停拆成若干次很短的暂停。

### 二、三色标记法：黑白灰

并发标记的经典抽象是三色标记，每种标记分别代表以下含义：

- 黑色：已经扫描完，它引用的对象都处理过了（确认存活）
- 灰色：已发现（可达），但它引用的对象还未处理完毕。
- 白色：还未被访问到，若标记结束仍是白色，则是垃圾。

具体流程为：

1. 初始时所有对象为白色
2. 从根出发，把直接可达的对象标灰
3. 取一个灰对象，扫描它的引用，把引用的白对象标灰，自己转黑
4. 重复第三步，直到没有灰色对象。
5. 此时仍为白色的对象即为垃圾。

### 三、并发带来的问题

上面那套流程在STW时没有问题，但并发标记肯定是并发运行的。假设出现以下情况

#### 漏标：误删活对象

假设当前应用有以下引用

```text
Root → A → B → C     
           D<──┘
```

在标记进行到B时，A被标记为黑，B是灰色，C和D都是白色，对象C引用D。
此时应用线程做了一件事：取消C对D的引用，添加对象A对D的引用，变成了

```text
Root → A → B → C     
       └──>D
```

此时标记进行到C，将C变成灰色，发现C没有引用任何东西，于是将C标黑。
至此，ABC都是黑色，没有灰色对象，此时GC认为标记已经结束，但此时被A引用的D还是白色。这将导致D被误删，导致程序出错。

#### 多标：保留垃圾

同样的情况

```text
Root → A → B → C     
           D<──┘
```

在B被标记黑色的时候，C变为灰色。此时应用断开B到C的引用，但C已经被标为灰色，因此C和D在这一轮扫描都会被留下来。这就是多标带来的浮动垃圾，苟活的对象在下一轮GC时会被清除，因此基本无害。

### 四、如何解决漏标

我们注意到，发生漏标必须同时满足两个条件：

1. **赋值器插入了一条或多条从黑色到白色对象的新引用；**（黑→白）
2. **赋值前删除了全部从灰色到该白色对象的直接或间接引用**（灰→白的路径）

所以只需要破坏任意一个条件即可避免漏标发生，由此衍生出两个解决方案

1. 增量更新（破坏条件1）：发生黑引用白的写入时，把该黑色对象重新标灰，等待重扫
2. 原始快照（破坏条件2）：当引用被删除或者覆盖时，记录旧的引用（快照里活着就算活着）

### 五、写屏障的角色

这些方案一般都依赖写屏障（write barrier） 实现，这里的概念和维护跨代引用的写屏障机制是一样的，都是通过插入小段代码更新卡表。

### 六、两方案对比

两种方法各有优劣，增量更新并发标记流程如下

```
1. 初始标记（STW，很短）
2. 并发标记（和用户线程同时跑，不 STW）
3. 重新标记（STW，处理并发期间的引用变化）
4. 并发清理（和用户线程同时跑）
```

原始快照的并发标记流程如下

```text
1. 初始标记（STW，很短）
2. 并发标记（和用户线程同时跑）
3. 重新标记（STW，处理 SATB 队列）
4. 并发清理（和用户线程同时跑）
5. 并发重置（为下一次 GC 做准备）
```

核心差异如下

| 维度| SATB（原始快照）| IU（增量更新）|
| ---| ---| ---|
| 记录内容| **被删除的旧引用**| **新增的引用**（黑色对象指向白色对象） |
| 写屏障职责 | 覆盖前记录旧值| 写入后检查并记录黑色对象               |
| 重新标记工作 | 处理 SATB 队列中的旧引用对象   | 重新扫描被记录的黑色对象               |
| 漏标解决     | 按快照标记，保证旧引用对象存活 | 重新扫描新引用，补标白色对象           |
| 浮动垃圾     | **多**                         | **少**                                 |
| 重新标记 STW | **通常较短**                   | **可能较长**（取决于新增引用量）       |
| 写屏障开销   | **较低**                       | **较高**                               |
| 实现复杂度   | 较简单                         | 较复杂|

### 七、.NET的做法

Gen0/Gen1 采用 STW 回收，不做并发标记，因此不存在并发漏标。

并发标记在.NET的实现是 Gen2 的后台GC。写屏障" 只要往老代对象写引用就把其所在卡片标脏 "的规则，恰好覆盖了漏标的条件 1（黑色老代对象新增对白色对象的引用）；后台 GC 重扫脏卡片即可补标，从而顺手解决了漏标问题。

## 大对象堆

### 一、什么是大对象堆

.NET的托管堆是由两个堆组成：小对象堆和大对象堆。划分标准是对象大小，大于85KB的对象放入LOH，否则放入SOH。这个阈值是可以配置的，.NET Core可通过运行时配置调整。

### 二、LOH的价值

GC的压缩阶段会移动对象，移动成本与对象大小成正比。如果把大对象和小对象混在一起，每次回收都要搬运这些大对象。由于大对象的移动成本太高，所以应该尽量避免移动它们。

为此，.NET的解决方法很简单：把大对象单独拿出来放到一边，把这儿叫做LOH，并且默认不压缩（不移动对象）。
移动成本高，那我不动就是了。

### 三、LOH属于哪一代

一般情况下，LOH一创建就处于Gen2，逻辑上也被当作Gen2（文档里有时称之为Gen3，但只是物理意义上的，逻辑上还是Gen2）。因此，LOH只在Gen2回收时（Full GC）才会被扫描回收。

### 四、LOH的分配方式

由于LOH回收时不压缩，所以它原来占的那块内存会空出来，但不会被其他对象填上，形成一个可用区域。这块区域会被登记进入空闲列表（free list），分配时需要在该列表中寻找一个足够大的空闲内存。

### 五、LOH碎片化问题

由于LOH本身的回收机制与分配方式，在反复回收和分配交替进行时，空洞会越来越多，空间会越来越碎片化。这将导致一个问题：分配大对象需要一块连续的内存，但由于可用空间被切得零碎，可能会出现剩余空间足够，但由于不连续而无法继续分配。

这将带来几个问题：

- 内存浪费
- 进程内存占用偏高
- 极端情况下抛`OutOfMemoryException`

那么解决方法就很显而易见了，那就是——**在需要时，允许压缩一次LOH**。

.NET Framework 4.5.1 起 / .NET Core 都支持这个开关：

```C#
using System.Runtime;

GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce; //压缩一次
GC.Collect();   // 下一次完整 GC 会压缩 LOH，把空洞填掉
```

## GC模式

GC模式可以拆分成两个独立的维度：

- 堆的结构：工作站GC / 服务器GC ，这决定了：用几个堆、几个GC线程、优化延迟还是吞吐
- Gen2是否并发：后台GC / 阻塞GC

### 一、工作站GC / 服务器GC

对于工作站GC

- 它的目标是低延迟，响应快，主要面向桌面端与客户端使用。
- 一般只有单个托管堆，GC用单线程执行。
- 暂停相对较短，适合用户能感知卡顿的场景

对于服务器GC

- 它的目标是高吞吐量
- 每个CPU核心一个堆+一个GC线程，多个堆并行回收
- 暂停时间可能更长，但总吞吐量更高

### 二、后台GC / 阻塞GC

后台GC：

- 针对Gen2，在专用后台线程上与应用线程并发执行标记
- 期间应用线程可以继续跑
- 取代了早期的并发GC
- 在后台GC进行期间，如果Gen0/Gen1需要回收，会触发foreground GC，它是阻塞的。

阻塞GC：

- 关闭后台GC时，Gen2回收完全STW
- 暂停更长，但实现更简单、内存占用可能更可控

## GC优化手段

### 一、GC成本

想要优化GC，首先要知道GC的成本是从哪里来的

GC的开销大致正比于：分配量 × 存活对象量。所以优化就有三个方向

1. 减少分配
2. 减少存活对象——让对象尽早回收
3. 降低单次回收成本


下面细讲具体实现方式

### 二、减少分配

1. 热路径里避免无谓的new

   ```C#
   // 循环里每次都分配，需要避免
   for (int i = 0; i < n; i++)
       Process(new List<int>());

   // 复用同一个对象
   var list = new List<int>();
   for (int i = 0; i < n; i++)
       Process(list);
   //Process()指代某种处理函数，这里没有实际意义。
   ```

2. 避免装箱

   装箱会把值类型搬到堆上，是隐蔽的分配来源

   ```C#
   object o = 42;              // 装箱 → 堆分配
   string s = 42.ToString();   // 不装箱（有重载）
   ```

   优先使用泛型而非`object`，让值类型不装箱

   ```C#
   void M<T>(T x) { }   // 泛型：值类型不装箱
   void M(object x) { } // object：值类型会装箱
   ```

3. 字符串拼接

   如果使用“+”号，每次都会新建字符串：

   ```C#
   string s = "";
   for (int i = 0 ; i < n ; i++) s += i;
   ```

   使用StringBuilder


   ```C#
   var String_B = new StringBuilder();
   for (int i = 0 ; i < n; i++) String_B.Append(i);
   string s = sb.
   ```

### 三、池化复用

池化解决了反复分配的问题，而是把现有的借出来用、用完还回去 。

`ArrayPool<T>` （最常用）

```C#
var pool = ArrayPool<byte>.Shared;
byte[] buffer = pool.Rent(1024);
try
{
    // 使用 buffer
}
finally
{
    pool.Return(buffer);
}
```

注意：`Rent` 返回的数组 可能比请求的大 ，要用返回长度而不是自己假设的大小。

其他池：

- `MemoryPool<T>` ：面向`Memory<T>` 的池；
- `ObjectPool<T>` （Microsoft.Extensions.ObjectPool）：对象池。

### 四、用`Span<T>`/ 值类型 减少堆分配

`Span<T>` /`ReadOnlySpan<T>` ：栈上的"视图"，切片/截取 零分配 ：

```C#
ReadOnlySpan<char> span = str.AsSpan(0, 5);   // 不产生新字符串
```

`stackalloc` ：小缓冲直接在栈上分配，不进堆：

```C#
Span<byte> buf = stackalloc byte[256];
```

`struct` ：值类型，若无装箱则在栈上（或内联），不增加 GC 压力。

### 五、避开 LOH 分配
之前提过，大于 85,000 字节的对象进 LOH ，而 LOH 只在完整 GC 回收、默认不压缩、易碎片化 。

所以对大缓冲区， 优先用`ArrayPool<T>` 复用 ，而不是反复`new byte[100000]` ：

```C#
// 差：反复在 LOH 上分配大数组
byte[] buf = new byte[100_000];

// 好：从池里借，避免 LOH 分配和碎片
byte[] buf = ArrayPool<byte>.Shared.Rent(100_000);
```

### 六、让对象尽早变成垃圾
- 缩小作用域 ：变量声明在需要的地方，让它在方法早期就出作用域；
- 及时清引用 ：长生命周期容器里，用完就把元素置`null` /`Remove` ，别让短命对象被长期持有；
- 警惕缓存 ：无上限的缓存会让对象"永远存活"，本质是内存泄漏。
