# 一、进程

## 1.什么是进程

程序是磁盘上的静态可执行文件，进程是程序的一次**动态执行实例**。同一个程序可以运行出多个进程，每个进程拥有独立的代码、数据、资源和进程 ID。**进程是操作系统分配资源的基本单位。**

## 2.进程的内存空间与资源

一个进程在运行时，并不是只占一块内存。操作系统会为每个进程分配一套**独立的地址空间**，并在其中划分出不同区域，同时管理它持有的各种系统资源。

### 2.1进程的虚拟地址空间

现代操作系统通常给每个进程提供一个**独立的虚拟地址空间**。32 位进程的地址空间总量通常是 4GB，但其中用户态可用部分一般为 2–3GB（取决于操作系统，例如 32 位 Windows 默认 2GB）；64 位进程的地址空间则大得多。

> **每个进程都以为自己独占整个地址空间，但实际上操作系统通过页表把虚拟地址映射到物理内存。**

所以进程 A 的地址 `0x1000` 和进程 B 的地址 `0x1000`，虽然虚拟地址相同，但映射到的物理内存通常不同。
这就是进程之间**内存隔离**的基础。

### 2.2进程地址空间的分区

一个进程的虚拟地址空间从高到低通常包含：

- 栈：局部变量，函数调用信息
- 堆：malloc/new动态分配
- BSS（未初始化数据）：未初始化的全局/静态变量
- Data：已初始化的全局/静态变量
- roData（只读数据/常量区）：字符串字面量、只读常量
- 代码区：程序指令

除此之外，进程地址空间里还有：

- 共享库映射区：比如`libc.so`、`kernel32.dll`等动态库被映射进来
- 内核空间：用户进程不能直接访问，由操作系统管理

这些区域的具体布局和增长方向根据平台的不同而有差异

### 2.3进程隔离

进程之间默认是隔离的，一个进程不能直接访问另一个进程的内存；一个进程崩溃通常不会导致另一个进程崩溃；进程如果想共享数据，必须通过操作系统提供的进程间通信机制。

这种隔离带来了安全性，也带来了通信成本。

## 3.进程的创建与终止

### 3.1进程的创建

进程通常由另一个进程创建。创建者叫`父进程`，被创建者叫`子进程`。

- 在 Linux/Unix 上，所有进程的祖先是`init`进程（现代系统可能是`systemd`），PID为1.
- 在 Windows 上，由`CreateProcess`API创建，父进程通常是`explorer.exe`或命令行。

用户双击程序、命令行执行命令、启动服务，本质上都是某个父进程请求操作系统创建子进程。

### 3.2进程的终止

#### 进程完成任务后正常退出

- C/C++ 中 `main` 返回
- 调用`exit()`
- C#中`Environment.Exit()`

正常终止时，进程会释放打开的文件和资源、刷新缓冲区、向父进程返回退出码

#### 进程因错误异常终止

- 段错误：访问非法内存
- 除零
- 未捕获异常
- 被信号杀死，比如`SIGKILL`、`SIGSEGV`
- Windows上的未处理异常导致进程崩溃。

异常终止时，进程不会正常清理资源，但操作系统会回收它占用的内存、文件描述符等。

#### 父进程等待子进程

在 Unix/Linux 中，子进程终止后不会立即消失，而是变成**僵尸进程**，等待父程序读取它的退出状态。

#### 孤儿进程

父进程先终止，子进程仍在运行，这些子进程叫做“孤儿进程”，它们会被系统中的`init`进程收养，继续运行，不会变成僵尸进程。

### 3.3退出码

进程终止时会返回一个整数退出码，为0通常表示成功，非0表示失败，具体含义由程序定义。

## 4.进程间通信（IPC）

进程之间默认是隔离的，但实际环境中程序经常需要协作，比如浏览器主进程和渲染进程、数据库服务器和客户端、多个后台服务之间，都需要交换数据。
操作系统为此提供了一组机制，统称为**进程间通信（Inter-Process Communication，IPC）**。

### 4.1常见IPC方式

#### 管道

管道是最古老的IPC方式之一，本质上是一块由内核管理的内存缓冲区，分为匿名管道和命名管道。在 Unix 上两者都是单向的（一次数据流只能沿一个方向）；Windows 的命名管道则支持双工通信。

---

#### 消息队列

消息队列允许进程以消息为单位发送和接收数据。

- 每个消息有类型和优先级
- 接收方可以按类型选择消息
- 内核维护队列，进程可以异步读写

相比管道，消息队列保留了消息边界，更适合结构化通信

---

#### 共享内存

共享内存让多个进程**映射同一块物理内存**到各自的地址空间

**优点**是速度快，因为数据不需要在用户态和内核态之间复制，适合大量数据共享

**缺点**是需要手动同步，通常需要配合信号量使用，容易引入竞态条件

---

#### 信号量

信号量本身不传输数据，而是用于同步和互斥：

- 控制多个进程对共享资源的访问
- 常与共享内存配合使用
- 限制并发数量

信号量内部通常有两个部分：

1. **一个整型值 count**：表示当前可用资源的数量；
2. **一个等待队列**：当资源不足时，等待的进程/线程会挂在这里。

对信号量的操作只有两种，且都是**原子操作**：

| 操作   | 常见名称                  | 作用                                          |
| ------ | ------------------------- | --------------------------------------------- |
| P 操作 | `wait`、`acquire`、`down` | `count--`，如果 `count < 0`，当前进程阻塞等待 |
| V 操作 | `signal`、`release`、`up` | `count++`，如果有进程在等待，唤醒一个         |

“**原子操作**”意味着这两个操作不会被其他进程打断，多个进程同时操作也不会出问题。

---

#### 信号

信号是一种**异步通知机制**，名字和信号量相似，但两者完全不同。

信号用于通知进程某个事件发生，比如`SIGINT`、`SIGTERM`、`SIGKILL`。

信号携带的信息很少，通常只是一个编号。

---

#### 套接字（Socket）

套接字不仅可以跨网络通信，也可以用于同一台机器上的进程间通信。

- Unix域套接字：本机进程间通信，效率高；
- TCP/UDP套接字：跨机器通信

通用性最强的IPC方式，支持双向通信、流式和数据报模式

---

#### 内存映射文件

把一个文件映射到进程地址空间，多个进程映射同一个文件时，就相当于共享内存

- 可以持久化数据
- 纯内存共享
- Windows 和 Linux都支持

### 4.2IPC核心问题

无论哪种方式，IPC都要解决以下问题：

1. 数据传输：怎么把数据从A送到B
2. 同步：怎么知道对方什么时候读，什么时候写
3. 互斥：多个进程同时访问共享资源的时候怎么避免冲突
4. 命名与发现：进程怎么找到对方，比如通过PID、文件路径、端口、键值
5. 权限与安全：哪些进程允许通信

## 5.进程调度与状态

进程不是一直占着 CPU 运行的。操作系统需要在多个进程之间分配 CPU 时间，让它们“看起来”同时运行。这就涉及**进程状态**和**调度**。

### 5.1进程的典型状态

一个进程通常会在几种状态之间转换：

```text
        创建
         │
         ▼
        就绪 ←──────────┐
         │              │ 时间片用完 / 被抢占
         │ 被调度        │
         ▼              │
        运行 ───────────┘
         │        │
         │        └──────→ 终止
         │ 等待 I/O 或事件
         ▼
        阻塞
         │
         │ 事件完成
         ▼
        就绪
```

1. 创建：

   程序刚被创建，正在分配资源、初始化PCB

2. 就绪：

   进程已准备好运行，等待CPU；多个就绪进程会排在就绪队列中

3. 运行：

   进程正在CPU上执行。单核CPU同一时刻只有一个进程处于运行状态

4. 阻塞：

   进程因为等待某个事件而暂停，比如等待IO、等待锁、等待信号。即便CPU空闲，它也不能运行

5. 终止：进程执行结束或被强制kill，等待父进程回收或系统清理。

关键转换：

- 就绪 → 运行：被调度器选中；
- 运行 → 就绪：时间片用完或被更高优先级进程抢占；
- 运行 → 阻塞：主动等待事件；
- 阻塞 → 就绪：等待的事件完成；
- 运行 → 终止：正常退出或异常终止。

### 5.2调度器做什么

调度器负责从就绪队列中选择一个进程，把CPU分配给它，调度时需要考虑：

1. 公平性：每个进程都有机会运行
2. 吞吐量：单位时间内完成更多进程
3. 响应时间：交互式进程要尽快响应
4. 周转时间：从提交到完成的时间尽量短
5. CPU利用率：尽量不让CPU空闲

这些目标之间往往会冲突，所以不同系统使用不同调度策略

### 5.3常见调度算法

#### 1. 先来先服务（FCFS）

按就绪顺序运行，先到先得。

- 简单；
- 但长任务会阻塞后面的短任务，平均等待时间可能很长。

#### 2. 短作业优先（SJF）

优先运行预计执行时间最短的进程。

- 平均等待时间较小；
- 但需要预知运行时间，且长任务可能饥饿。

#### 3. 时间片轮转（Round Robin）

每个进程运行一个固定时间片，用完就放到就绪队列末尾。

- 适合交互式系统；
- 时间片太大退化成 FCFS，太小则上下文切换开销大。

#### 4. 优先级调度

给进程分配优先级，高优先级先运行。

- 可能导致低优先级进程饥饿；
- 常用“老化”技术逐步提高等待过久进程的优先级。

#### 5. 多级反馈队列

设置多个优先级队列，进程根据行为在队列间移动。

- 新进程进入高优先级队列；
- 用完时间片还没结束，降到低优先级队列；
- I/O 密集进程留在高优先级，保证响应；
- 现代通用操作系统常用类似思想。

### 5.4抢占式与非抢占式

- **非抢占式**：进程一旦运行，除非它主动阻塞或结束，否则一直运行到完成。
  FCFS、SJF 常见于早期系统。
- **抢占式**：调度器可以在时间片用完或更高优先级进程就绪时，强制切换 CPU。
  现代通用操作系统基本都支持抢占，保证响应性。

### 5.5上下文切换

当CPU从一个进程切换到另一个进程时，需要保存当前上下文，恢复下一个进程的上下文。上下文一般包含以下信息：

- 程序计数器
- CPU寄存器
- 栈指针
- 页表基址
- 其他硬件状态

上下文切换有开销，应根据应用场景决定是否使用该策略，以及使用时的时间片长度

# 二、线程

## 1.什么是线程

### 1.1线程的基本定义

线程是**进程内部的一条执行流**。

一个进程至少有一个线程，也可以有多个线程。多线程在同一个进程内并发执行，共享进程的大部分资源，但各自独立执行。

可以理解为：

> 进程是资源分配的基本单位，线程是CPU调度的基本单位

操作系统调度CPU时，调度的对象是线程，而不是整个进程

### 1.2线程的组成

每个线程都有自己独立的一套执行上下文

- 程序计数器：当前执行到哪条指令
- 寄存器状态：CPU寄存器的值，线程切换时需要保存和恢复
- 栈：每个线程有自己的调用栈，存放局部变量、函数参数、返回地址等。
- 线程ID：操作系统或运行时分配的标识
- 线程局部存储（TLS）：每个线程独立的数据副本
- 状态信息：就绪、运行、阻塞等状态。

线程共享的是进程的资源，包括：代码段、全局变量、堆内存、打开的文件描述符、当前工作目录、信号处理表等。

### 1.3简单例子

```cpp
#include <thread> //C++11线程类标准库
#include <iostream>

int global = 0;   // 全局变量，所有线程共享

void work(int id) {
    int local = id * 10;   // 局部变量，每个线程栈上独立
    global++;              // 修改共享数据
    std::cout << "线程 " << id
              << " local=" << local
              << " global=" << global << std::endl;
}

int main() {
    std::thread t1(work, 1); //创建一个新t1线程，执行work(1)
    std::thread t2(work, 2); //创建一个新t2线程，执行work(2)

    t1.join();//主线程阻塞等待，直到t1执行完毕
    t2.join();//主线程阻塞等待，直到t2执行完毕
}
```

> **注意：这个例子故意展示未同步的共享写入。`global++` 是“读-改-写”三步操作，多线程同时执行会产生数据竞争，输出里的 `global` 值不可预期。正确做法见 4.1 的互斥锁。**

### 1.4多线程意义

多线程主要用于：

1. **提高 CPU 利用率**
   一个线程等待 I/O 时，其他线程可以继续运行。
2. **利用多核 CPU**
   多个线程可以真正并行执行。
3. **提高响应性**
   GUI 程序中，主线程保持界面响应，后台线程处理耗时任务。
4. **简化某些并发模型**
   比如服务器为每个连接创建一个线程。

但多线程也带来复杂性：竞态条件、死锁、调试困难、上下文切换开销等。

## 2.线程的生命周期与状态

### 2.1线程的典型状态

一个线程通常经历以下状态：

```text
        创建
         │
         ▼
        就绪 ←──────────┐
         │              │ 时间片用完 / 被抢占
         │ 被调度        │
         ▼              │
        运行 ───────────┘
         │        │
         │        └──────→ 终止
         │ 等待锁、I/O、条件变量等
         ▼
        阻塞
         │
         │ 等待的事件完成
         ▼
        就绪
```

可以看到，线程的状态与进程是非常相似甚至一模一样的。不同的是阻塞条件，线程会因为等待某个事件而暂停，比如：

- 等待互斥锁
- 等待条件变量
- 等待IO
- 等待其他线程
- 睡眠

### 2.2状态转换

- **就绪 → 运行**：调度器选中该线程；
- **运行 → 就绪**：时间片用完，或被更高优先级线程抢占；
- **运行 → 阻塞**：线程主动等待某个事件；
- **阻塞 → 就绪**：等待的事件完成；
- **运行 → 终止**：线程函数返回或异常终止。

阻塞的线程不会直接变成运行，而是先回到就绪队列，等待再次被调度。

### 2.3一个例子

```cpp
#include <thread>
#include <iostream>
#include <chrono>

void work() {
    std::cout << "工作线程开始\n";
    std::this_thread::sleep_for(std::chrono::seconds(2));
    std::cout << "工作线程结束\n";
}

int main() {
    std::thread t(work);

    std::cout << "主线程等待工作线程\n";
    t.join();   // 主线程阻塞，直到 t 结束
    std::cout << "主线程继续\n";
}
```

### 2.4线程终止方式

1. **正常返回**
   线程函数执行完毕，线程自然终止。
2. **异常退出**
   线程函数抛出未捕获异常，整个程序终止。
3. **被取消**
   C++ 标准库没有直接提供线程取消机制。
   POSIX 有 `pthread_cancel`，但使用需谨慎，容易导致资源泄漏。
4. **主线程退出**
   如果主线程结束而其他线程还在运行，程序可能直接终止，导致其他线程被强制结束。

所以通常要确保所有线程在 `main` 返回前结束，或者被 `detach` 后妥善管理。

## 3.线程的创建与销毁

不同语言创建线程的方式不同，但核心都是：**指定一个入口函数，让操作系统或运行时创建一个新的执行流**。

以C#为例，下面是线程从创建到销毁的全流程

### 3.1 C# 中创建线程的常见方式

#### 3.1.1`Thread`类

```csharp
using System.Threading;

void Work() {
    Console.WriteLine("工作线程");
}

Thread t = new Thread(Work);
t.Start();      // 启动线程
t.Join();       // 等待线程结束
```

带参数

```csharp
Thread t = new Thread(() => Work());
t.Start();
```

#### 3.1.2`Task`/`Task.Run`

现代C#更推荐`Task`：

```csharp
using System.Threading.Tasks;

Task t = Task.Run(() => {
    Console.WriteLine("任务在线程池线程上执行");
});

t.Wait();   // 等待任务完成
```

`Task.Run`会把工作放到线程池，通常比手动创建`Thread`更高效。

#### 3.1.3`ThreadPool`

```csharp
ThreadPool.QueueUserWorkItem(state => {
    Console.WriteLine("线程池工作项");
});
```

适合大量短小任务，避免频繁创建销毁线程

#### 3.1.4`async/await`

```csharp
async Task DoWorkAsync() {
    await Task.Delay(1000);
    Console.WriteLine("异步完成");
}
```

`async/await` 不直接创建线程，而是基于 `Task` 的异步模型，通常配合线程池使用。

### 3.2C# 线程的销毁

C#的`Thread`对象：

- 线程函数返回后，线程自然结束；
- 不推荐使用 `Thread.Abort()`，它在 .NET Core/.NET 5+ 中已不支持，且容易导致资源泄漏和状态不一致；
- 推荐用取消令牌 `CancellationToken` 协作式取消。

```csharp
CancellationTokenSource cts = new CancellationTokenSource();

Task.Run(() => {
    while (!cts.Token.IsCancellationRequested) {
        // 工作
    }
}, cts.Token);

cts.Cancel();   // 请求取消
```

## 4.线程同步——互斥锁、条件变量、信号量、原子操作

多个线程共享同一进程的内存，直接并发读写共享数据会产生**竞态条件**。线程同步是为了协调线程的执行顺序、保护共享资源的机制。这个机制解决的核心问题就是：**在并发环境下，保证共享数据被正确、有序地访问。**

为了实现这一点，同步主要包含两个方面：

- 互斥：同一时刻只允许一个线程访问某段代码或某个资源。目的是防止多个线程同时修改共享数据。
- 顺序控制：让线程按照某种预期顺序执行。目的是为了解决谁先谁后的问题。

### 4.1互斥锁

互斥锁的作用是保护临界区，同一时刻只允许一个线程进入。临界区是指一段访问共享资源的代码。

关键性质：

- **互斥性**：同一时刻只有一个线程持有锁。
- **所有权**：谁加锁，谁负责解锁
- **阻塞等待**：拿不到锁的线程会休眠，不占用CPU

互斥锁适合保护“一小段会修改共享数据的代码”。锁的粒度要小，临界区要短，否则并发度会下降。

C++中最常用的是`std::mutex`:

```cpp
#include <mutex>

std::mutex mtx;
int shared = 0;

void work(){
    std::lock_guard<std::mutex> lock(mtx); //加锁，离开作用域自动解锁
    shared++; //临界区
}
```



C#中对应的是`lock`语句或`Monitor`:

```csharp
private readonly object _lock = new object();
private int _shared = 0;

void Work() {
    lock (_lock){
        _shared++;
    }
}
```



### 4.2条件变量

有些场景的情况不是“不能同时访问”，而是“现在还不能做，要等待某个条件触发”。

比如消费者从队列取数据，下意识的做法是：循环检查队列，如果为空就继续查，否则取出来用。但这种循环检查本身是**忙等**，会浪费CPU资源。

条件变量就是用来解决这个问题：

- 当消费者发现条件不满足，就进入等待状态，释放锁，让出CPU资源
- 生产者改变条件后，发出通知；
- 消费者被唤醒，重新检查条件，成立则继续

关键点：

- 条件变量本身不保存“条件”，条件由共享变量表示
- 等待时必须配合互斥锁，因为“检查条件”和“进入等待”必须是原子的
- 被唤醒后要**重新检查条件**，因为可能被虚假唤醒，或者条件又被其他线程改变了

条件变量解决的是顺序控制的问题

```cpp
#include <mutex>
#include <condition_variable>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> q;

void producer(){
    {
        std::lock_guard<std::mutex> lock(mtx);
        q.push(1);
    }
    cv.notify_one(); //通知一个等待者
    //notify_all() 唤醒全部
}

void consumer(){
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock,[]{return !q.empty();}); //等待条件成立
    int value = q.front();
    q.pop();
}
```



### 4.3信号量：同时能有多少个

信号量是一个计数器，表示当前可用的资源数量

- 计数大于0：线程可以获取资源，计数减一
- 计数等于0：线程需要等待
- 有线程释放资源时，计数加一，并唤醒等待者

和互斥锁的区别：

互斥锁只有锁与未锁两种状态，只有一个线程能使用资源，信号量则是计数，可以允许不超过上限的线程数同时进入。

C++中提供`std::counting_semaphore`

```cpp
#include <semaphore>

std::counting_semaphore<3> sem(3);  // 最多 3 个线程同时进入

void work() {
    sem.acquire();   // P 操作，计数减一，不足则阻塞
    // 访问最多 3 个并发资源
    sem.release();   // V 操作，计数加一，唤醒等待者
}
```

在C#中

```csharp
SemaphoreSlim sem = new SemaphoreSlim(3);

await sem.WaitAsync();
try {
    // 最多 3 个并发
} finally {
    sem.Release();
}
```



要点：

- 信号量不关心“谁释放”，任何线程都可以 `release`；
- 适合连接池、限流、生产者-消费者中的缓冲区计数；
- 计数为 0 时，`acquire` 会阻塞。

### 4.4原子操作：轻量同步

有些共享数据操作非常简单，比如计数器加一、标志位置位。如果为这种操作单独加一把锁，开销可能会很大。

原子操作保证某个操作不可分割：要么完全执行，要么完全没有执行，中间不会被其他线程打断或插入。由于这个性质，适合给简单计数器、bool标志、单个指针或整数的无锁更新

如果涉及到多个共享变量，或需要检查条件后修改，这时原子操作就不够了，仍然需要锁。

C++中`std::atomic`

```cpp
#include <atomic>

std::atomic<int> counter{0};

void work() {
    counter++;              // 原子自增
    counter.fetch_add(1);   // 显式原子加
    int value = counter.load();  // 原子读
}
```

C#中`Interlocked`

```csharp
private int _counter = 0;

void Work() {
    Interlocked.Increment(ref _counter);
    int value = Interlocked.CompareExchange(ref _counter, 0, 0);
}
```

要点：

- 原子操作不会被其他线程打断；
- 适合计数器、标志位、简单状态切换；
- 不能替代复杂临界区，多个变量需要一起保护时仍然要用锁；
- 有内存序（memory order）概念，默认 `seq_cst` 最安全但开销较大。

## 5.线程安全与竞态条件

### 5.1什么是线程安全

一个函数或对象被称为**线程安全**，是指：

> 多个线程**同时调用**它时，**不需要额外的同步措施**，它仍然能**表现出正确的行为**。

- **同时调用**：不是串行调用；
- **不需要额外同步**：调用者不用自己加锁；
- **正确行为**：结果符合预期，内部状态不被破坏。

线程安全不是“绝对安全”，而是相对于某个使用场景的保证。

### 5.2线程安全的级别

#### 5.2.1不可变（Immutable）

对象创建后状态永不改变，因此天然线程安全，可以随意共享。

例如C#的`string`、不可变集合等。

#### 5.2.2无状态（Stateless）

函数不依赖也不修改任何共享状态。

例如纯计算函数，`int Add(int a, int b)`，多个线程同时调用没有问题

#### 5.2.3线程安全

内部有共享状态，但通过锁，原子操作等机制保证并发调用正确。

例如`std::mutex`保护的计数器

#### 5.2.4有条件线程安全

某些操作安全，某些操作需要调用者额外同步

例如`std::vector`的`const`方法可以并发读，但并发写需要加锁。

#### 5.2.5非线程安全

多个线程同时访问会出问题，调用者必须自己同步。

大多数普通容器和自定义类属于这一类。

### 5.3竞态条件的典型形态

竞态条件是指程序的正确性依赖于线程执行的相对时序。常见形态有：

- **检查后执行**

  ```text
  if(queue 非空){
      取出元素
  }
  ```

  两个线程可能同时判断不为空，然后都去取，第二个取的时候队列已经空了。

  这类问题的本质是：**检查和执行之间，对象的状态可能被改变**

- **读-改-写**

  ```text
  counter = counter + 1;
  ```

  上面一行代码分为读、加、写三步，多个线程可能交错执行，导致丢失更新。

- **惰性初始化**

  ```text
  if (instance == null){
      instance = new Singleton();
  }
  ```

  两个线程都可能判null，各自创建一个实例，破坏单例。

- **发布逸出（unsafe publication）**

  一个线程正在构造对象，另一个线程就拿到了它的引用，可能看到未完全构造的对象

- **复合操作**

  多个看似独立的操作组合在一起，中间可能被其他线程插入，导致整体不一致。

### 5.4如何判断是否线程安全

- 有没有**共享可变状态**
- 有没有多线程**同时读写同一份数据**
- 有没有**检查后再操作**的逻辑
- 有没有**多个变量需要保持一致**
  即使每个变量都用原子操作，多个变量之间仍可能不一致，需要锁保护整体。
- 有没有**发布对象引用**

### 5.5线程安全常见思路

#### 5.5.1减少共享

尽量用局部变量、线程局部存储、避免共享可变状态。

#### 5.5.2使用不可变对象

不可变对象天然线程安全，可以自由共享

#### 5.5.3封装同步

把锁、条件变量封装在类内部，对外提供线程安全的接口，而不是让调用者自己加锁

#### 5.5.4缩小临界区

锁只保护需要保护的代码，减少阻塞

#### 5.5.5避免复合操作的竞态

把“检查+修改”做成原子操作，或者用锁保护整体

#### 5.5.6非线程安全声明

如果类不是线程安全的，要明确写出调用者需要同步，避免误用。

## 6.线程池与常见并发模型

### 6.1线程池基本结构

- 工作线程集合：固定数量或可动态调整的线程
- 任务队列：存放待执行的任务
- 调度逻辑：把任务分发给空闲线程
- 生命周期管理：启动、停止、等待任务完成

工作流程：

```text
提交任务 → 任务队列 → 空闲工作线程取出任务 → 执行 → 继续取下一个
```

如果所有工作线程都在忙碌，新任务就在队列中等待

### 6.2常见并发模型

线程池是基础设施，上层通常由几种并发模型来决定如何使用线程池

#### 6.2.1任务并行模型

把工作拆成多个独立任务，提交到线程池并行执行。

这种处理方式适合批量处理数据，关联不大的任务。

#### 6.2.2生产-消费者模型

生产者把任务放入队列，消费者从队列中取出执行。线程池本身就可以看作一种生产-消费者结构

这种方式适合处理：

- 任务到达速度不均匀
- 需要解耦生产与消费
- 需要缓冲与限流

#### 6.2.3事件循环/Reactor模型

一个或少数几个线程负责监听事件，事件到达后分发给处理逻辑。常见于网络服务器、GUI程序

特点：

- 避免为每个连接创建线程
- 用非阻塞IO和事件多路复用
- 适合高并发IO密集场景

#### 6.2.4Actor模型

每个Actor是一个独立的执行单位，拥有自己的状态和消息队列。Actor之间通过发送消息通信，不共享内存

特点：

- 天然避免内存竞态
- 消息串行处理，单个Actor无需内部锁

#### 6.2.5数据并行模型

把大量数据分成多个块，多个线程分别处理不同数据块

适合：

- 数组、矩阵运算
- 图像处理
- 按数据切分计算

### 6.3线程池的常见问题

- **长时间阻塞任务占满线程池**

  线程池被阻塞时无法执行其他任务，可能导致饥饿。长时间阻塞任务应使用独立线程或异步IO

- **任务之间共享状态需要同步**

  线程池只负责调度，不负责数据同步

- **异常处理**

  任务中未捕获的异常可能导致线程终止或程序崩溃，需要统一捕获处理。

- **死锁**

  某些任务需要等待另一个任务的结果，几个线程（或任务）之间相互等待，就会导致死锁

- **线程池大小不合适**

  过小无法充分利用CPU，太大会增加调度和内存开销


# 三、协程

## 1.什么是协程

协程本质上是一个函数，是一种**可以被挂起和恢复的例程**。普通函数只能一次调用、一次返回，协程却可以在中途让出控制权，之后再从断点继续执行；何时暂停、何时恢复，都由程序员决定。


特点：

- 主动让出：协程自己决定在哪里暂停，而不是被操作系统抢占
- 保留状态：暂停时，局部变量、执行位置都保留
- 恢复执行：可以从上次暂停的地方继续，而不是从头开始

协程在**用户态**由程序自己调度，这一点常被类比为“用户态线程”；但“用户态线程”通常指有独立栈、由用户态调度器切换的实体，而协程强调**协作式让出**，无栈协程甚至没有独立栈，两者并不等同。协程也不是线程的替代品。
协程通常在**单个线程**内协作运行，适合I/O密集、需要大量并发但不想创建大量线程的场景。

## 2.协程的分类

协程的分类主要有两个维度：**控制流的转移方式**以及**是否拥有独立栈**

### 2.1对称协程与非对称协程

这个维度看的是：协程把控制权交给谁

#### 2.1.1对称协程

协程暂停后，可以把控制权交给**任意其他协程**，彼此地位平等，例如

```text
协程 A 暂停 → 切换到协程 B
协程 B 暂停 → 切换到协程 C
协程 C 暂停 → 切换回协程 A
```

特点：

- 协程之间是对等关系
- 需要一个调度器决定下一个运行谁
- 控制流转移更加灵活，但管理更加复杂

代表：Modula-2 的协程（提供单一的 transfer 操作）。注意 Lua 的协程属于非对称模型，见 2.1.2。

#### 2.1.2非对称协程

协程暂停后，只能把控制权交回**调用者**，之后也只能由调用者再次恢复，例如

```text
调用者 → 协程 A 开始
协程 A 暂停 → 返回调用者
调用者 → 恢复协程 A，从暂停处继续
```

特点：

- 协程和调用者之间是主从关系
- 控制流简单，容易理解
- 大多数语言采用这种模型

代表：C#的`async/await`、Python的`async/await`、C++20的协程。这些实现通常由编译器改写为状态机，属于“无栈 + 非对称”（见 2.2.2）。

### 2.2有栈协程与无栈协程

这个维度看的是：协程暂停时，执行状态保存在哪里。

#### 2.2.1有栈协程

每个协程都有**独立的调用栈**。

暂停时，整个栈被保留；恢复时，从原来的栈继续执行

特点：

- 可以在协程内部任意深度的函数调用中暂停
- 实现简单直观
- 每个协程需要分配栈空间，内存开销大
- 协程数量受栈大小限制

代表：Lua协程、Go的goroutine（栈由运行时管理）、部分C++协程库。

#### 2.2.2无栈协程

协程**没有独立栈**，暂停状态保存在堆上的状态机或帧对象中。

编译器把协程函数改写成状态机：

- 暂停时保存局部变量和当前状态；
- 恢复时根据状态跳转到对应位置

特点：

- 内存开销小，可以创建大量协程；
- 只能在**协程自身的挂起点**（如 `await`、`yield`）暂停；一旦进入普通（非协程）函数调用，就无法在其中途挂起
- 编译器需要做状态机转换，实现较为复杂
- 通常与`async/await`配合。

典型：C++20协程、C#的`async/await`、Rust的`async`。

### 2.3两者的组合

| 组合          | 控制流     | 栈       | 典型代表                                                                 |
| ------------- | ---------- | -------- | ------------------------------------------------------------------------ |
| 非对称 + 无栈 | 交还调用者 | 无独立栈 | C# `async/await`、Python `async/await` 与生成器、C++20 协程、Rust `async` |
| 非对称 + 有栈 | 交还调用者 | 独立栈   | Lua 协程、Boost.Coroutine2 等                                            |
| 对称 + 有栈   | 任意切换   | 独立栈   | Go goroutine（栈由运行时管理）                                           |
| 对称 + 无栈   | 任意切换   | 无独立栈 | 较少见                                                                   |

## 3.使用场景与常见误区

### 3.1常见应用场景

#### 3.1.1IO密集型任务

网络请求、文件读写、数据库查询。

协程在等待IO时暂停，不阻塞线程，一个线程可以驱动大量并发请求。

#### 3.1.2UI编程中的异步操作

C#的`async/await`在UI线程上发起异步操作，等待时界面不卡顿，完成后自动回到UI线程更新控件。

#### 3.1.3生成器与惰性求值

`yield return`按需产出数据，适合处理大集合、无限序列、流式数据处理，避免一次性分配大量内存

#### 3.1.4游戏开发中的状态机与定时逻辑

Unity的协程（`IEnumerator`+`yield return`）通常用于按帧等待、延时执行、动画序列、关卡脚本。

#### 3.1.5高并发服务器

用少量线程驱动大量协程，每个连接一个协程，代码写法接近同步，但实际是非阻塞的。

### 3.2常见误区

#### 3.2.1协程不是线程

协程通常运行在线程之上，由程序协作式调度。不会自动利用多核CPU，要并行执行CPU密集型任务，仍然需要多线程或并行库。

#### 3.2.2协程不能消除阻塞

如果协程内部调用了阻塞操作，比如同步IO、`Thread.Sleep`、长时间计算，它仍会阻塞底层线程。协程的优势在于“在等待时让出线程”，而不是让阻塞操作消失

#### 3.2.3不要用协程处理CPU密集型任务

协程适合IO密集和等待型任务。
CPU密集型任务应该用多线程、并行算法或线程池，协程对此不能帮上忙，反而会增加状态机开销

#### 3.2.4忘记取消和释放

长时间运行的协程如果不再需要，应该支持取消。

C#用`CancellationToken`，C++需要自己设计取消机制。否则协程可能一直挂着浪费资源

#### 3.2.5在协程中共享可变状态仍需要同步

协程运行在单个线程内时，通常不需要锁。但如果多个线程各自运行协程，并且共享数据，仍然需要同步。协程不自动解决竞态条件。
